## 2026-08-29：冷静期兑现的不是心情，是「顺路记的结论会过期」

**中心论点**：

> 这天 audit 真正的产出不是给两篇笔记定了个名字，是三条 08-02 / 08-16 记下的「已核查」结论，一个月后重查全都不够准。冷静期的价值不在等心情冷下来，在于**换成「马上要动手」的眼光重跑一遍**。

### 一、三次翻案，都是同一个 pattern

| 当时记的 | 08-29 重查发现 |
|---|---|
| 「归纳优先框架已有三篇」（08-16）| 实际是「两对厚薄版」——v2→PWPE、书接上回→Ni-Te-audit。n 的口径本来就错 |

共同点：这三条当时都是**做别的事时顺路记下的**（08-02 在 audit moc、08-16 在 audit `!q-` 全表），没有真跑一遍 grep。08-29 因为要真动手移文件了，才跑了完整核查。

所以「顺路记的核查结论」和「动手前跑一遍的核查」不是一回事——前者带着当时那个任务的视角偏差，只看得见跟当时任务有关的那部分。**记录里写「已确认」三个字的时候，得同时记下当时是怎么确认的**，否则下次会把它当既成事实用。

顺带一条操作层的：grep 查链入要覆盖 `docs/*.md` + `docs/archive/*.md` + 根目录 `*.canvas` + `.claude/skills/`，别只查 docs 下的 md。这次全库扫出 14 条历史死链，全是往次归档只移文件没修路径欠下的。

### 二、命名：先查自己的词库，别造一个准确的词

给 `!distill-` 定名时提的三条要求：英语开头 / 不能排到 book- 后面 / 突出完全自己产出。

前两条是硬约束，第三条差点让人去造词。实际解法是反过来的——**先翻自己已经在用什么词**：`distill` 早就在 `raw/eBook/00-distilled/` 和 `print/distill-note-*.docx` 里用了，不是新造的。

而第三条要求，最后**没有写进字面**：按 07-12 定的分工（AI 只能拆自己的脚手架，内容的读薄跑不了自己一个字一个字敲），蒸馏这个动作压根不可能外包，所以前缀本身就是署名。

这条可以推广：**新东西要命名时，先问库里已有的规矩能不能承载它的一半意思**。能承载的那半不用写进名字，名字只留必须由它承担的部分。这样名字短，而且跟已有体系天然咬合。

多字母而不用 `!d-`，是因为单字母跟 `h`、`q` 容易混——`!q-` / `!h-` 各自只有一个字母够用，是因为当时只有两个；到第三个就该换规格了。

### 三、判据说破：`!` 分的是「谁写的」，`_` 分的是「不是我写的」

给 `!distill-` 找位置时才发现，`!` 前缀家族一直有一条没说破的判据：

- `!q-` / `!h-` / `!distill-` = 我自己的东西（我提的问题、我押的假设、我蒸的版本）
- `_inbox` / `_overview` / `_todo` / `_toRead` = 被动基础设施

这条区分库里一直在用，只是从没写下来。写下来之后，`!distill-` 归在 §2.4 自我认知层而不是加工层就顺理成章了——**它的判据是「谁写的」，不是「讲什么」**。同一天做的导航层三分（moc / dashboard / 索引）用的是另一条判据「打开它时你在做什么动作」。两条判据各管一层，不冲突。

### 四、`_todo` 重构成 todo / pending 两章

原来四章（任务清单 / 等待信号 / `!q-`-`!h-` 全表 / 待读清单）混在一个文件里，「已退出记录跟 todo 这个名字冲突」——但真问题不是已退出（编号是稳定 ID，退出的号不复用，必须留一行说去哪了）。真问题是**一个文件同时干两件事：动作清单 + 状态表**。

所以不拆成三篇，改成两章各自标清：`1. todo`（在做什么）+ `2. pending`（在等什么，是 dashboard）。原「等待信号」与「`!q-` / `!h-` 全表」合并进 `2. pending`，因为两者是**同层**不是相邻层——句式完全一样：信号 1 等「cluster 11 第 2 篇 ref 出现」，C001 等「第 2 本批判精英思维的社科书」。

**没拆成三篇的依据是耦合度**：§一 主线的「下一步该做什么」5 条里 4 条直接引用 §三 的编号（Q004 / H001-003），拆开等于每次看主线都要开另一个文件；而待读清单跟前三章互不引用、全库也没有第三篇引用它，所以只有它拆得出去（→ `_toRead.md`）。

**判拆不拆，先量耦合度，别凭「感觉这两块不是一回事」。**

#### 同一天第二刀：todo 章的三个档也取消了

`1. todo` 底下原有 🟡 该抽时间做 / 🟠 稳定推进 / 🟢 接近完成 三档。作者的诊断：「稳定推进项有一堆，其实很多都是**稳定的没有推进**」，而且「接近完成和完成的边界又在哪里？」

病因是**三个档用了三种不同判据**——🟡 是工作形态（一次性 vs 持续）、🟠 是节奏（不催）、🟢 是完成度。三种判据混在一个轴上，边界必然模糊：🟠 的定义「有时间就做，不催」不排除任何东西，所以成了什么都往里扔的地方；🟢 更站不住，**完成度不是状态、是进度百分比**，任何任务都会路过「接近完成」，那条边界根本不存在。

改法不是重新命名档位，是逐条问「它不动是因为什么」。12 条里只有 6 条真是「能做但没做」：4 条其实在等条件（进 §2.1 信号 8/9/10 与 §2.2 说明），2 条不是独立任务（一条附着在别的动作上，一条是说明行）。剩下 6 条摊平成一个按顺序排的列表，判据只剩一条：**能做，缺的只是时间**。

**副作用是有意留的**：一条待办如果既不缺条件又长期不动，摊在一个列表里就藏不住了——它要么该排到最底下，要么根本不是想做的事。当天就抓出一个：《枪炮、病菌与钢铁》归纳挂了一个多月，理由写的是「和 v2 没接口，不急」，而 v2 当天已经归档，这个理由本身失效了。

#### 这一天的三次合并，用的是同一条判据

| | 合还是拆 | 依据 |
|---|---|---|
| §二 等待信号 + §三 `!q-`/`!h-` 全表 | 合 | 都是「在等触发」，句式一模一样 |
| §四 待读清单 | 拆 | 服务的是另一条工作流（选书 → 批量读 → 横向对比），零耦合 |
| 🟡 / 🟠 / 🟢 三档 | 合 | 移走等条件的之后，剩下的全是「能做没做」，状态一样就不需要档 |

**先问「这两块是不是同一个动作」，是就合、不是就拆。** 跟同日给 `!distill-` 定判据（先问有没有厚版原件）是同一种做法：不按内容分，按动作分。

#### 附：`_todo` 里那些说明文字的去留

## 2026-07-30：内化从 moc 入手，不逐张重写 card；认知觉醒 ≠ 能力圈

card 作为最小单元，想整合它们的话就会漂向 moc 式的链接，所以应该分成两件事：card 单纯的内容瘦身 + card 再理解。现在新产出的一个逻辑链条：PWPE（为什么）→ 刻意练习（怎么故意制造对的预测误差）→ Ni-Te-audit（做什么）适合作为一个 moc。如果把这个 moc 作为主线，然后用到什么概念，再去单个的 card 做重写计划，更合适一些。顺序上，不是说每一张 card 都可以 cover 所有 use case、moc 只需要从 card 里抽取即可；而是说以问题为导向产生 moc，通过 moc 不断加深对单个概念的理解，不断完善 / 新产出反复出现的概念。对于 moc 的问题，有一个问题主干是有必要的，但真正完善后的问题，是要在整篇文章结束后收束得到的。最后，通过 _scratch 逐渐呈现出一个 insight：「认知觉醒 ≠ 能力圈 / 模型是果、行动是因」。

### 背景

上周把 [moc-@认知链路-v2](archive/moc-@认知链路-v2.md) 打印成纸质版，反复读了几遍。发现 v2 本身重复很多、有为了凑结构强行成文的地方，读着尴尬。真正的产出其实已经在 canvas v2 锚点图里列出来了（6 条），但它们缺论据、更像边缘型的扩展。于是决定从 v2 里最熟、却一直卡住的那一点入手——PWPE 和贝叶斯更新的关系——写成了 !DRAFT 的前五章；顺势又起了第六章行动层。

### 一、!DRAFT 里作者自己压出来的产出（4 个，怎么归类下周再定）

1. **感知层流程图（误差在先、精度在后）**：v2 用二维坐标轴，这里改成流程图，并定了顺序——先看预测误差一不一致，再看预测精度高不高。这个顺序里藏着坐标轴表达不出的一个差别：误差能直接拿到（概率一比就有），精度拿不到、只能靠直觉隐式感觉。它和全篇"非对称"主干对上了——连获取这两样信息本身都是不对称的。
   - 提醒：这张图是"做决策的人"的视角，不是大脑神经计算的顺序（神经上精度是并行地给误差加权，不分先后）。别哪天拿它去讲大脑怎么算。
2. **PWPE 对应边际效应**：PWPE 对应边际效应 → 大脑在算经济账 → 经济账要算的就是非对称结构 → 于是有了那 5 个非对称模型。这是感知层往决策层过渡的那一步，是这篇真正的新产出，也是"归纳优先框架"该有的那种中心论点（跨贝叶斯 / 边际效应 / 非对称三者合成一句话，比 v2 那个混合 SCQA 的中心论点更尖）。
3. **PWPE 定性决策清单（哪些加分、哪些减分）**：把"算经济账"落到能上手的加减账。加分＝讲收益的 4 个（二八 / 长尾 / 复利 / 临界点），减分＝讲成本和风险的（二阶 / 战略性懒惰 / 机会成本 / 逆向）。
   - 顶一句：把每个模型钉死在一个正号或负号上是一种简化，代价是抹掉了它们本是"看问题的角度"。机会成本（正文里写的是"决策的背面、隐性框架"）、逆向思考都是角度、不是固定扣分项。当 checklist 用没问题，但记得它把角度压成了条目——这正是作者批 v2 的"为了凑结构"，这次发生在自己手里。
4. **直觉（Ni）也可以 tracking**：行动层那套模板本身是精度膨胀（没有 tracking 对象就先起模板），但它带出一个真发现——tracking 不只服务 Si（客观事实，如手账）和 Fe（关系，如 NVC），Ni / 直觉也能 tracking。做法不是直接记摸不着的直觉，是记直觉做出的可检验预测（行动前"把直觉转成陈述性假设"那步），事后拿实际结果一对、反推直觉准不准、回去调它的先验精度。它正好补上 6-27 记的那条闭环：模型 → 行动 → 用 tracking 结果回头修正模型，其中"回头修正"这一路对 Ni 是通的。
   - 结论：模板先搁着（精度膨胀），"直觉可 tracking"这个发现留下来。

### 二、比笔记内容更大的三条过程教训（都是 Te——拿经验回头修自己的方法）

1. **引用 ≠ 理解，自己用文字输出过才算理解。** 贝叶斯更新和 PWPE 大概今年年初就进库了，后面很多笔记都在引用，可半年过去才发现理解一直不到位——因为从没自己用文字输出过。这类"引用得很熟、却从没自己写过一遍"的概念/笔记，很可能还有很多（Claude CLI 让扩充变容易后，很多 card / toolkit 从没回看过）。
   - 改法不是"别偷懒"（靠意志力，违背战略性懒惰）：是流程里缺一个逼自己输出的环节。可操作的小信号——**下次要引用一个概念前，先问：我自己用文字输出过它吗？** 没有就进"该读薄"清单。撞一个逮一个，不必大动干戈做全库 audit。
2. **写完的成就感不是质量信号，是多巴胺在奖励"完成"这个动作。** v2 去脚手架后 2w1 字，翻来覆去最后只压得出 6 条 !q-；写成时很有成就感，冷静后现在几乎想全推翻。这个成就感，恰好是 !DRAFT 里写的多巴胺机制——它奖励"完成"、不奖励"写对"。上一轮的"打通感"、这一轮的"成就感"，是同一个东西。

## 2026-05-06：Canvas 在 PKM 体系中的位置

> **来源声明**：本节由 Claude 代写，基于 2026-05-06 与作者关于 Obsidian Canvas 第一次实战的讨论整理。作者负责 review 与最终判断。

### 引言

作者 5 月 5 日决定先沉淀已有的 !q- / card / moc，开始用 Obsidian Canvas 做可视化 review。第一张画布建好后，作者发现一个重要的认知：**Canvas 不只是看笔记的工具，它是 PKM 体系里一个之前缺失的层**。

---

### 一、Canvas 的真正位置

之前作者把笔记分成几类：book / ref（输入）、card / toolkit（加工）、tracking（过程）、moc（导航）、!q-（开放问题）。这些都是"已经成形的"内容。

Canvas 补的是另一种东西——**正在成形中的关系**。它处在内容节点之间的关系层，让作者可以**先把关系画出来，再决定是否把它写成稳定的 card 或 moc**。

可以这样描述各类笔记的"结晶程度"：

- 输入态：book / ref
- 探索态：**Canvas**（关系流动，可随时改）
- 半结晶态：!q-（问题清楚但答案未定）
- 已结晶态：card-@（单概念稳定）
- 已合成态：toolkit-@
- 已导航态：moc-@（文字版）

Canvas 是上游探索工具，其他类型是下游沉淀成果。

---

### 二、Canvas 不能完全替代文字笔记

讨论中作者的两点澄清：

**1. card 仍然必要**

当一个概念已经被反复确认稳定（在多张 Canvas 上重复出现、关系清楚），它就该有一个稳定的文字载体——就是 card。Canvas 是临时视图会过时，card 是长期参考。

**2. 文字版 moc 仍然必要**

Canvas 上画的关系图属于"我现在的解读"。但 moc 是问题导航地图，需要稳定的文字陈述驱动问题、引导到具体笔记。Canvas 是 moc 的可视化辅助，**不是替代**。

---

### 三、Canvas 可能改变协作模式（仅作可能性，不固化）

之前作者和 Claude 的协作是：Claude 写半成品 → 作者填 TODO 沉淀。

5 月 6 日讨论中浮现一种新的可能性：**作者在 Canvas 上画关系（找到框架）→ Claude 写完整笔记 → 作者 review**。

这个新模式的好处是：框架是作者自己画的，逻辑已在脑里；视觉化的关系比文字更易理解；Claude 写的细节正好补盲点。

但 Canvas 才刚开始用，一个月内不可能产出大量画布，**这个模式还需要更多实战才能确认是否真的更好**。当前不固化为协作规则。

---

### 四、本次唯一确定的一句

> **要找关系，就用 Canvas；要稳定结论，写文字。**

---

### 五、给自己的提醒

- 不急着改变协作模式——先用 Canvas 自然画几张
- Canvas 上同一组关系反复出现 → 提炼成 card 的信号
- Canvas 上同一组节点反复成簇 → 提炼成 moc 的信号
- 不要追求"漂亮 Canvas"——画图是为了消化，不是为了好看

---

## 2026-05-05：关于"沉淀"和"加机制"的两难

> **来源声明**：本节由 Claude 代写，基于 2026-05-05 与作者关于 _todo P1（A1+A2 tracking 方法论）的讨论整理。作者负责 review 与最终判断。

### 引言

作者准备开始做 _todo §一 P1 的 A1+A2（tracking 方法论 + 行动→提炼闭环）。和 Claude 讨论一轮后，方案从"给 tracking 加 metadata + 每月 audit + 概念激活机制"逐步收缩，最后变成几乎不动现有体系。这个**收缩本身**就是这次的核心 lesson。

---

### 一、几条核心 lessons

**1. tracking 其实就是特定类别的 inbox**

讨论中作者突然意识到：inbox 和 tracking 用的是同一个机制——最小阻力记录 + AI 后置判定。区别只在 inbox 是临时态（目标是清空），tracking 是持续态（目标是累积）。

这个观察让整个体系更连贯——所有"输入"类内容都遵循"先记录后结构化"的统一原则。

**2. AI 结构化的产出不能污染流水账**

作者担心：如果给 tracking 每条记录都加 metadata 字段（applied / verdict / update），后面回看的时候要绕过这些结构化字段才能看流水，违反最小阻力原则。

解法是把 AI 反馈做成 tracking 文件末尾的独立索引区，和流水账用一道分隔线隔开。但这一轮先不动——等第一次真跑 audit 时再加。

**3. 不要在用户消化期间加新机制**

作者最关键的一条 tension：这几天高强度对话产出了大量新建的 !q- / card / moc / toolkit，但还没时间沉淀。再加 audit 机制会过载。

Claude 之前默认 "AI 协作 = 帮用户做更多事"。这次作者反过来指出：**复利的引擎不是 AI 多干活，是 AI 知道什么时候让用户独自待一会**。

这条改变了后面所有具体决定：audit 改成触发式（用户说"帮我 audit"才跑）、代写笔记改成半成品（只填核心字段，其他留 TODO）、tracking 文件结构延后到真需要时再动。

**4. Claude 代写的笔记应当留半成品状态**

作者反思：哪怕全程 review 过 Claude 代写的内容，"看一遍就过"的浅层 review 让笔记停留在 Claude 的认知里，没真进作者的认知。

解法：未来 Claude 代写 !q- / card / moc / toolkit 时，只填核心字段（锚点句 + 主张力），其他字段留 TODO。让作者在沉淀过程中自己填——填的过程就是吸收的过程。

这条作为新 memory 已写入（feedback_audit_and_drafting）。

---

### 二、给自己的提醒

- 当前阶段不要再让 Claude 加新机制——已有 !q- / card / moc / toolkit / 候选池 / 工具决策自检 都还没用过几次
- 有"4 类 tracking 之外的散点" 时扔到 [_inbox](_inbox.md) §临时记录，等下一次主动触发 audit 时再分流
- 想跑 audit 时主动说一句话（"帮我 audit / 复盘 tracking / 看看 inbox 临时记录"）——AI 不会主动催
- 给自己几周时间沉淀，然后再决定下一步加什么 / 不加什么

---

### 三、本次最重要的一句

> 复利的真正引擎不是 AI 多干活，是 AI 知道什么时候让用户独自待一会。

## 2026-05-04：与 Claude 五十多回合对话之后的几条记录

> **来源声明**：本节由 Claude 代写，基于 2026-05-02 至 05-04 期间作者与 Claude 的对话整理。作者负责 review 与最终判断。

### 引言

最近三天作者和 Claude 高强度对话，把笔记体系做了一次大改造。改完之后，作者让 Claude 帮自己复盘一下"哪些经验以后能反复用"。下面是 Claude 整理的几条。

---

### 一、和 AI 对话这件事

**1. AI 最有用的时刻，不是回答问题，是帮你看清你真正想问的是什么**

作者在 5 月 1 日写了一篇笔记，七成篇幅都在纠结要不要加 Notion、Obsidian 怎么用。Claude 反过来指出：作者顺手写下的两条 ToDo（如何追踪 tracking、如何把 lessons 变成 checklist）才是真问题。前面所有的工具讨论，其实都是在绕开这两条。

作者后来自己说过一句话："答案的好坏取决于对问题的描述。"——这就是它的另一面。和 AI 对话最值钱的瞬间，不是它给你答案，是它帮你重新问。

**2. 写下一条原则，不等于以后会照着做**

5 月 1 日作者刚写完"不要再陷入鼓捣笔记软件陷阱"，紧接着在同一篇笔记里就开始认真考虑加 Notion。

写在卡片上的原则只是档案。它要真起作用，得绑定到一个具体动作（比如"我考虑加新工具的时候"）+ 一组强制问题。原则得变成"钩子"才能拦得下人。

这就是后来 [toolkit-@工具决策前的自检](toolkit-@工具决策前的自检.md) 的由来。

**3. Claude 代写的笔记和作者自己写的笔记，留下的痕迹不一样**

哪怕作者全程 review 过 Claude 写的内容，"看懂了"和"自己想出来的"，在脑子里留下的印记不是一回事。

所以约定：所有 Claude 代写的内容，开头都要写一句来源声明。这不是走形式，是防止几年后回看时，把 Claude 的推论错记成自己的洞察。

---

### 二、关于笔记体系本身

**4. 命名错了几个月，纠正只要半小时**

`atom-` 这个前缀用了几个月。它来自"原子化笔记"的概念，但作者实际用它来写开放问题，两件事根本不是一回事。每次写新笔记、向 AI 解释，都会有一点点别扭。

改成 `!q-` 用了 30 分钟。但消除的是这几个月里几十次回访时悄悄累积的摩擦。

教训：命名要尽早调对。错命名的代价是慢慢攒出来的，等你发现的时候已经付了很多。

**5. 二选一往往不够，要找第三档**

这次对话里反复出现这种情况：

- 不是"升级成 !q-"或"不升级"，而是"强升级 / 弱候选池 / 留 inbox"
- 不是"保留"或"删除"，而是"分流 / 归档 / 删除"
- 不是"重要"或"不重要"，而是艾森豪威尔的四象限

当一个判断只有两个选项的时候，多半是还没想透。强迫自己列第三个选项，往往会发现真实情况需要的就是那个第三档。

**6. cluster 是事后归纳的，不是事前过滤的**

作者一度担心：新笔记的主题不在现有 12 个 cluster 里怎么办？

Claude 提醒：作者 4 月 30 日那次分类本来就是先有 90 篇笔记、再归出 12 个 cluster——不是先建 cluster 再往里塞。所以处理孤立主题的方法是：先入库，把它链到最相近的 cluster；等同类第 3 篇出现，再自然形成新 cluster。

这条对所有"分类系统"都成立——分类是事后归纳工具，不是事前过滤器。

**7. 不要在跑通流程之前就优化**

作者一度想先把 metadata 设计、标题模板、card 数量都规划好再开始用。Claude 不同意：跑一篇真实的 ref 暴露出来的痛点，比预想的"可能问题"靠谱得多。

后来跑了 [ref-暖暖熊-如何读书读论文读教材读代码](ref-暖暖熊-如何读书读论文读教材读代码.md) 那篇，确实暴露出 7 个 README 不够用的卡顿点——其中有 4 个是事前完全想不到的。

教训：先用，再修。预防"可能的问题"几乎一定是浪费精力。

---

### 三、关于回访这件事

**8. 写下来不等于会被读到**

这次新建的几个东西都带回访机制：候选池有"升级信号"，`!q-` 有"待回看条件"，待读清单按 cluster 分区（这样撞到锚点 book 时容易触发）。

它们做的是同一件事：**没有触发条件的笔记 = 信息坟墓**。

知识管理的复利不来自"读了多少书"，而来自"留下了多少未来的自己能认出'这个值得回头看'的痕迹"。

---

### 四、给自己的提醒

- 候选池里挂的 3 条（二八规律 vs 简化论 / 大一统 / 形而上学）要真回看，否则就是新的 inbox
- [moc-@决策杠杆](archive/moc-@决策杠杆.md)、[toolkit-@让系统1为我所用](toolkit-@让系统1为我所用.md) 这些升级，要被实战验证。一两个月后回看：完全没用到，就是精度通胀，该降级或归档
- `tracking-@` 方法论（A1+A2）是下一阶段重点，按 [_todo](_todo.md) P1 启动
- 别再陷入"先把所有规则定完再用"。已经 review 过 [toolkit-@工具决策前的自检](toolkit-@工具决策前的自检.md) 了，下次冒出"加新工具"冲动时去走一遍 5 问

## 2026-05-02：被 Claude 反诊断后才发现的真问题

## 2026-05-01：与 Claude 对话——cluster / moc / card 体系的渐进式重构

### 起点

90 篇笔记，按认知负荷只能常看 10 篇。表面问题：管理困难、AI 味儿重的笔记懒得读、按学科分类后发现没意义。

### 一、想法的几次反转

**反转 1：分类问题 → 库存问题**

最初我想按"认知层 / 行动层 / 系统层"分类。Claude 反问：90% 笔记从未被回访——这不是分类问题，是**库存问题**。我接受，提出 hot/cold 活跃层思路，限定 10 篇。

**反转 2：冷存档 → 未挖矿石**

我意识到：AI 味儿重的笔记我留着，是期望某天 AI 帮我发现 insight（曾尝试 notebooklm 但因主题太散失焦）。Claude 建议四层结构（活跃 / 矿区 / 文学回响 / 冷存档），矿区按聚焦主题成簇投喂。

**反转 3：自己一晚就把 90 篇分成 12 个 cluster**

我能凭标题回忆内容——证明笔记不是死的，是**缺触发器**。

**反转 4：cluster ≠ moc**

我以为每个 cluster 都要建 moc。Claude 澄清：

- **cluster = 静态聚类**（物理归簇，无独立文件，存于 `_overview.md` 章节）
- **moc = 问题导航**（必须有驱动问题）

多数 cluster 不需要 moc。现存 6 张 moc 中，只有 [moc-@认知链路](archive/moc-@认知链路.md) 和 [moc-@人性矩阵](moc-@人性矩阵.md) 严格符合定义；其余实际是 dashboard 或 cluster 索引。这一区分写入了 `README §3` 和 `note-intake` agent。

反转 5：表面是 inbox 整理，深层是 tracking 定义混乱

`tracking-@<书名>` 这种"按书做容器"的形式实际承载了 4 种性质不同的内容（思考片段 / 多模型桥接 / 概念结晶过程 / 行动追踪）。我问 Claude 一个根本问题：**知识的最小单元是概念/模型？**

Claude 确认。需要补 `card` 层——这是体系真正缺的一环。

**反转 6：5 张 keystone card 试水（节奏 C）**

不大改 90 篇旧笔记，只挑 5 个核心概念建 card：

我以为是格式问题（emoji / 序号）。Claude 拆开：**写作流和 review 流应该分工**。Typora 适合写不适合 review；Obsidian 的 Graph view / Canvas 才是 review 工具。所有工具都基于 markdown，可同时打开同目录，不需迁移数据。

### 三、最重要的几个判断

1. **笔记的组织轴是概念/主题/模型，不是书**——书只是 input。
2. **cluster ≠ moc ≠ card**——物理归簇 vs 问题导航 vs 单概念结晶；三层语义不同，混用即混乱。
3. **moc 必须有驱动问题**，否则只是个名字花哨的目录。
4. **Don't multi-purpose tools**——Typora 写、Obsidian review、card 是 concept 单元、moc 是 navigation 单元。每个工具 / 笔记类型负责一件事。
5. **AI 味儿的笔记不是垃圾，是未结晶的素材**——补 card 层后，它们成为 toolkit/card 的喂养源。
